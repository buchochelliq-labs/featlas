# Feature Engineering Specification 0.2.0

Status: proposed contract and reference verification bundle. Schema dialect: JSON Schema Draft 2020-12.

This specification describes feature meaning, source relationships, temporal correctness, and the evidence an implementation must produce. It is not a deployed feature platform. The included verification kit establishes only the coverage recorded in its verification report.

## 1. Normative language and authority

**MUST**, **MUST NOT**, **SHOULD**, and **MAY** express requirements, recommendations, and permissions within this contract. Requirement identifiers beginning `SEM-` are stable references for diagnostics, tests, and review.

The authoritative structural definition is [schemas/project.schema.json](schemas/project.schema.json). This document and [the semantic rule register](docs/SEMANTIC_RULES.md) define additional invariants that JSON Schema cannot establish. Neither layer overrides the other: a conforming project must satisfy both. An implementation encountering a conflict must report it and stop the affected operation; it must not silently choose a convenient interpretation.

The schema `$id` under `https://example.org/feature-engineering-spec/0.2.0/` is an identifier, not a promised hosted registry. All shipped references must resolve locally. Network retrieval is unnecessary for validation.

## 2. Conformance has separate levels

| Level | What it establishes | What it does not establish |
| --- | --- | --- |
| Parse | The document is a valid instance of the restricted YAML or JSON profile. | References, feature meaning, or data correctness. |
| Structure | Required fields, allowed fields, types, enums, and local discriminated shapes satisfy the schema. | Unique business keys, reference resolution, DAG correctness, or executable capability. |
| References and types | IDs, references, versions, types, lineage, time rules, and contracts are internally consistent. | Whether real source rows satisfy the contract. |
| Planning and capabilities | A named, versioned implementation can preserve required semantics for the selected target. | Permission to run it or evidence that it has run. |
| Data and fixture | Supplied rows, histories, and golden outputs satisfy declared invariants for the evaluated cases. | All future rows, cloud execution, or operational SLOs. |
| Runtime and acceptance | The exact implementation candidate ran against named inputs and met explicitly checked requirements. | Untested targets, untested features, or future availability. |

**SEM-CONF-001:** Reports MUST state which levels were attempted, passed, failed, unsupported, or not evaluated. “Valid” without a level is insufficient. An unsupported operation is not a passing test. A fixture is not independent evidence when its expected values are generated by the same algorithm being checked.

**SEM-CONF-002:** A failure at a prerequisite level MUST block dependent execution. Informational descriptions and extension metadata MUST NOT authorize additional execution, network access, or data access.

## 3. Document and identity model

The root has `spec_version`, `kind: FeatureEngineeringProject`, `metadata`, `entities`, `sources`, `relationships`, `features`, `feature_sets`, `consumers`, `deployments`, and `acceptance_suites`. The schema defines which collections can be empty.

**SEM-PARSE-001:** YAML MUST contain a single document, string mapping keys, JSON-compatible scalar values, and no duplicate mapping keys. Anchors, aliases, merge keys, and custom tags are prohibited. Timestamps MUST be quoted strings. Non-finite numbers, implicit environment expansion, and executable interpolation are prohibited. Readers MUST apply this profile before JSON Schema validation; permissive “last key wins” parsing is nonconforming.

Schema `default` annotations do not insert missing values. A conforming reader MUST NOT silently supply undeclared semantic defaults. Any future explicit normalization/defaulting operation must be versioned and reflected in the canonical manifest.

**SEM-ID-001:** IDs MUST be stable, satisfy the schema's identifier syntax, and be unique within each collection, regardless of object version. This profile carries one version of an ID in each collection. IDs are case-sensitive; display names are not identities. Cross-kind collisions are allowed only because references identify their object kind.

**SEM-ID-002:** Every reference MUST resolve to exactly one object of the intended kind. A reference with an explicit version MUST match that object's version exactly. A version range, implicit latest version, or similarly named object MUST NOT satisfy an exact reference.

**SEM-ID-003:** The dependency graph of features MUST be acyclic. References in an expression to another feature MUST have matching declared dependencies and versions. Dependencies use the declared entity and as-of alignment; unrepresented cross-entity or shifted-time dependency semantics are unsupported.

**SEM-ID-004:** `spec_version` versions the document language. Object `version` fields version the meaning of a source, relationship, feature, set, consumer, or deployment. Compiler, runtime, SDK, custom implementation, and fitted artifact versions are separate evidence. Changing an implementation version does not automatically change feature meaning; changing feature meaning does require review and a new semantic version.

Descriptions, ownership, lifecycle status, and tags support discovery and review. They are not substitutes for machine-readable contracts. Core objects are closed to unknown fields. Namespaced `extensions` may hold additional metadata only. They MUST NOT alter baseline meaning or contain an executable override. Target-specific implementations use explicit `portability.native_bindings` and MUST preserve the referenced logical contract; genuinely different semantics require a reviewed language/object-version change.

## 4. Sources, columns, entities, and relationships

### 4.1 Logical source contract

A source records its human name and description, owner, version, column dictionary, primary key, record semantics, time columns, quality and retention contract, and provenance. Column descriptions MUST state what a value measures or identifies, including units and any non-obvious codes; “identifier” or “value” alone is insufficient when ambiguous.

**SEM-SRC-001:** Every referenced column MUST exist in the named logical source. Key, timestamp, revision, tombstone, validity, and lineage columns MUST have compatible types and nullability. Declared physical bindings MUST preserve their logical meaning, units, and timezone or include a reviewed normalization step upstream.

**SEM-SRC-002:** A primary key declares row identity. `record_semantics.logical_key` declares the identity reconstructed across revisions. These need not be the same: a stored revision may have a primary key including a revision number while the logical event key does not. Tenant identity MUST be part of all applicable logical keys and joins.

**SEM-SRC-003:** Actual key uniqueness, foreign-key coverage, null rates, valid ranges, and timestamp consistency are data checks. A schema declaration, primary-key annotation, or relationship cardinality is metadata until verified against the applicable rows. A target adapter MUST NOT infer that a storage system enforces a constraint merely because the contract declares it.

**SEM-SRC-004:** A source's provenance MUST identify upstream tables/files or other sources and the transformation/code reference when derived. A reproducible execution additionally needs immutable snapshots or equivalent versions, extraction parameters, and integrity evidence. An unversioned path is a locator, not an immutable input identity.

Source availability timestamps are insufficient when old revisions have been overwritten. `retention.raw_seconds`, `retention.revision_history_seconds`, and `retention.earliest_reproducible_at` constrain the supported historical interval. Runtime evidence MUST establish that the promised history is actually retained; an earlier request MUST fail rather than substitute today's state.

Physical table names, file paths, catalogs, and environment-specific targets belong in deployments. Credentials MUST remain outside specifications, fixtures, manifests, and generated code; bindings refer to externally managed identities or secret references only.

### 4.2 Population and entity grain

An entity declares a population source and maps every entity key to a source column. The population defines who is eligible to receive an output, including entities with no qualifying events.

**SEM-ENT-001:** Population rows MUST be evaluated as of the requested time using declared availability and activity semantics. Each eligible full entity key MUST identify one output row per feature/as-of request, unless the consumer explicitly preserves repeated observation rows with an additional observation identity. An event-only group-by MUST NOT silently remove entities with zero qualifying events.

Population completeness means the complete eligible key universe at T, not merely complete registration events within the feature's lookback window. A production adapter must establish that older still-active keys and subsequent deletions are retained or represented by an equivalent reconstructible state.

**SEM-ENT-002:** An entity's tenant key, if any, MUST be included in population identity, source grouping, dependencies, relationships, output keys, and consumer lookups. Tests MUST include equal local IDs under distinct tenants.

### 4.3 Relationships

Relationships explicitly identify directed source and target columns, cardinality, join type, unmatched behavior, multiple-match behavior, and temporal mode. A relationship declaration alone performs no join. A transform uses it by reference and binds left and right aliases.

**SEM-REL-001:** Join pairs MUST have equal arity and compatible types, represent the intended grain, and include applicable tenant keys. The aliases in a transform join MUST refer to the relationship's source and target. An input alias MUST be introduced exactly once and be reachable through the transform's declared joins when needed.

**SEM-REL-002:** Declared cardinality MUST be checked before a join can silently multiply an aggregate. The baseline permits only one-to-one and many-to-one relationships. Multiple matches are an error; an implementation MUST NOT choose an arbitrary row, first row, maximum value, or latest record as an undocumented repair. One-to-many relationships require a future version with explicit fan-out and aggregation semantics.

**SEM-REL-003:** A left join with `preserve_null` preserves the left row and represents unmatched right-side values as null. An inner join with `drop` removes unmatched rows. An `error` policy emits a diagnostic. Incompatible combinations MUST be rejected. Null equality keys do not match each other; `null_keys` declares whether they are unmatched or an error.

**SEM-REL-004:** Historical dimension joins MUST reconstruct the dimension as known at the feature cutoff and then apply its valid interval at the declared reference time. For `reference: left_event_time`, a right row is eligible only when its reconstructed interval contains the left event time. Versioned availability and valid time are different axes; using today's dimension, or an unrestricted “latest dimension row,” is nonconforming.

See [SOURCE_RELATIONSHIPS.md](docs/SOURCE_RELATIONSHIPS.md) for cardinality, revision, and temporal examples.

## 5. Temporal semantics

### 5.1 Three independent clocks

Let **T** be the requested feature `as_of` timestamp.

1. **Event time** determines whether an observation belongs to the feature window.
2. **Source availability time** determines whether an observation or revision was knowable by T.
3. **Feature publication time** determines whether a computed feature value could actually have been retrieved by a consumer at a given time.

All portable timestamps are UTC. Durations are integer elapsed seconds. A day-sized window means 86,400 elapsed seconds; it does not mean a calendar day in a local timezone.

**SEM-TIME-001:** For lookback W, the event window has lower endpoint T − W and upper endpoint T. `lower` and `upper` independently declare inclusivity. For example, `lower: exclusive` and `upper: inclusive` means T − W < event_time ≤ T. Implementations MUST test exact boundaries. `publication.delay_seconds` MUST NOT shift this event window.

**SEM-TIME-002:** Each source row or revision MUST satisfy the feature's availability cutoff, `available_time < T` or `available_time ≤ T` as declared. Event-time eligibility alone is insufficient. A record that happened before T but first arrived after T is unavailable for that historical computation.

**SEM-TIME-003:** A timestamp MUST be parsed and compared as an instant, not by text order. Reject invalid dates, timezone-less values, and unsupported precision rather than normalizing them silently. The portable profile uses UTC strings with a literal `Z` suffix and at most six fractional-second digits; a source adapter must normalize upstream timestamps before exposing them. A whole-second timestamp and the same timestamp with zero fractional digits compare equal.

### 5.2 Deterministic reconstruction and filtering order

**SEM-REV-001:** A versioned source MUST be processed in this order:

1. Select rows available at the feature cutoff.
2. Resolve physical primary-key duplicates under the declared policy, then partition by the complete `logical_key`.
3. Select the latest eligible revision according to the explicit lexicographic revision ordering.
4. Reject contradictory ties, invalid selected records, or otherwise ambiguous selection.
5. Apply the selected revision's tombstone policy.
6. Apply event windows, predicates, dimension validity, joins, and aggregation to the reconstructed records.

The ordering applies independently to each source. A selected correction can change event time, join keys, category, or amount. Filtering earlier can resurrect a superseded record or conceal a retraction. An invalid selected revision MUST produce a diagnostic; it MUST NOT cause fallback to an older valid revision.

**SEM-REV-002:** For append-only data, duplicate handling MUST follow the declared policy. `collapse_identical` may collapse truly identical records at the same identity; it MUST NOT mask conflicting payloads. `reject` requires a diagnostic. Deduplication is not equivalent to a feature's `count_distinct` operation.

**SEM-REV-003:** A dimension's logical record key MUST distinguish separate valid-time records that are allowed to coexist for the same entity. Revision selection by entity key alone is invalid when it would erase legitimate historical intervals. After reconstruction, overlapping eligible intervals that yield multiple matches MUST fail according to the relationship contract.

For the baseline half-open dimension interval, `valid_from ≤ reference_time < valid_to`; a null open-ended `valid_to` is permitted only where the column/contract allows it. Availability filtering occurs even when the validity interval covers the event time.

### 5.3 Reconstruction versus replay

**SEM-REPLAY-001:** `source_as_known` means recomputing from source records knowable at T. It does not prove that the feature was computed or served at T. Historical serving replay additionally requires immutable feature values or execution records with observed publication timestamps, selected semantic versions, and provenance.

**SEM-REPLAY-002:** A replay consumer MUST select only a value whose observed publication time is no later than the request time and whose feature version, entity keys, as-of semantics, missingness status, and freshness satisfy the consumer contract. Recomputing today, assigning T plus a configured delay, or reading a feature timestamp alone is not proof of historical publication. If publication evidence is absent, report the request as unsupported or not evaluable.

For the requested feature/version/entity, eligible publications satisfy `publication.as_of ≤ request.as_of` and `published_at ≤ requested_at`. Select the greatest tuple `(as_of, published_at, sequence)`. Duplicate complete ordering keys are an error. The latest eligible null supersedes an older non-null value; apply the consumer's preserve-null or reject policy without fallback. After selection, require `request.as_of − selected.as_of ≤ max_staleness_seconds`. A consumer of an atomic feature set additionally needs evidence that its member values belong to the same committed set snapshot.

**SEM-REPLAY-003:** Backfills and corrections MUST preserve historical publication evidence. A corrected value published today must not appear as if it had been available to a historical consumer. A publication delay is a scheduling contract; measured publication lag is runtime evidence.

## 6. Feature inputs, transformation, and output

Features declare an entity, output, aliased source inputs and used columns, version-pinned dependencies, time semantics, one transform, lineage, missingness, quality, history, and acceptance expectations.

**SEM-TRANS-001:** Every source column used in a predicate, expression, ordering, grouping, join, or coverage condition MUST be present in the input's declared columns. Every dependency referenced by an AST MUST be declared at the exact version and permitted alignment.

**SEM-TRANS-002:** Expression operators have fixed arity, supported input types, result types, and null behavior. Implementations MUST type-check before execution, reject unsupported operators, and never treat arbitrary SQL or Python strings as portable semantics. The schema enumerates the baseline AST shapes and operators.

**SEM-TRANS-003:** A filter retains only rows for which its predicate is true. False and null predicates do not pass. Null is not zero, false, or an empty string. Equality with null does not establish a match; use a supported explicit null-test operation where intended. Operators MUST preserve documented null propagation; `coalesce` is an explicit fallback, not a general null-to-zero rule.

**SEM-TRANS-004:** Aggregates are exact in this profile. `count` counts eligible records; `count_distinct` counts distinct tuples formed by `distinct_by`. Under `ignore`, tuples with any null component are excluded; `propagate` returns null when an eligible tuple contains null, and `error` fails. `sum`, `mean`, `min`, and `max` apply their declared null policy. Under `ignore`, eligible records with all-null values return null with state `ok` and require a nullable output; they MUST NOT invoke the known-empty identity. No eligible records invoke `missingness.empty` only after coverage is established. Approximate sketches and engine-default quantiles are outside the portable baseline.

**SEM-TRANS-005:** Recency is the nonnegative elapsed seconds between T and the latest eligible event time after reconstruction and filtering, rounded down using required `rounding: floor`. Thus 59.9 elapsed seconds yields integer 59. No eligible event invokes the feature's missingness policy; it is not an arbitrary large sentinel. Lookup selects the first row under its declared lexicographic ordering after eligibility checks. A remaining ordering tie MUST be diagnosed, even if values happen to be equal; a selected null remains null rather than causing fallback.

**SEM-TRANS-006:** Logical `integer` means signed 64-bit integer; `number` means finite binary64. Integer arithmetic is checked for overflow. Mixed integer/number operands may widen to number; strings and booleans do not coerce. Ordinary `divide` returns number and fails on zero denominator; `safe_divide` returns null for zero denominator. Other numeric operators propagate null. `and`/`or` use three-valued short-circuit logic, `coalesce` is lazy, and `if_else` evaluates only the selected branch, choosing else for a null condition. Non-finite results and integer overflow are diagnostics. Integer output tolerances are zero; number outputs declare absolute and relative tolerances. See the complete operator behavior in [SEMANTIC_RULES.md](docs/SEMANTIC_RULES.md).

**SEM-OUT-001:** Output values MUST satisfy declared type, unit, nullability, and range. Output names do not define their meaning. A change from dollars to cents, event count to distinct-user count, or one boundary convention to another is a semantic change even if the physical type stays the same.

## 7. Lineage and provenance

**SEM-LIN-001:** Feature lineage MUST identify each contributing source column and its role: value, filter, entity key, join key, event time, availability time, coverage, ordering, revision, deletion, valid time, or population. A column may have multiple roles. The explanation MUST describe how it affects the result. Missing time, key, revision, deletion, validity, coverage, or filter lineage is a correctness gap, even when all output values have lineage.

**SEM-LIN-002:** Lineage MUST include referenced feature versions and traverse to their source columns. For a derived source or custom operation, source/code provenance MUST connect the declared logical inputs to the actual execution artifact. The implementation MUST detect omitted dependencies and lineage references to nonexistent columns.

**SEM-LIN-003:** An execution manifest MUST distinguish declared lineage from observed lineage. It SHOULD record canonical specification hash, semantic object versions, exact code/build digest, source snapshots, fitted artifact digests, target capability report, parameters, output digest, and run/publication timestamps. Source row values and secrets must not be included in public manifests by default.

## 8. Missingness, coverage, and quality

**SEM-MISS-001:** These states MUST remain distinguishable in evaluation evidence: known empty eligible population, no qualifying events within verified coverage, insufficient history/coverage, null input values, unavailable source, unmatched relationship, unsupported computation, and execution failure. A user-facing result may combine states only through an explicit consumer policy that preserves their reason in diagnostics.

**SEM-MISS-002:** A zero event count is valid when the entity exists and the relevant source interval is known to be complete. Lack of rows alone does not establish completeness. `null` cannot prove “no events.” Source outage or execution failure MUST NOT be converted into a healthy zero.

**SEM-MISS-003:** Required history MUST be evaluated per entity/time when coverage differs by entity. Minimum rows, elapsed history, and completeness are different requirements. A source retention setting describes expected retention; runtime evidence must show that the requested interval is available.

Version 0.2.0 permits `history.coverage: contiguous` only. Required history must cover the feature window and be supported by positive external completeness evidence. Fixture `source_status` uses a half-open envelope `[coverage_start, coverage_end)`; it MUST contain the entire required interval. An inclusive feature upper endpoint at T requires `coverage_end > T`; an exclusive upper endpoint permits `coverage_end = T`. Status must cover every direct, transitive, and population source. Production adapters must also identify the tenant/partition scope, observation time, and status provenance. Partial or unknown coverage cannot produce a healthy zero.

**SEM-QUAL-001:** Quality contracts MUST identify their check, threshold, evaluation scope, and failure handling. Data checks include uniqueness, join cardinality, nullability, ranges, timestamp validity, completeness, and expected output grain. A monitoring alert threshold MUST NOT silently change feature values or delete failed rows.

## 9. Learned and custom transforms

The schema can describe a learned or custom transform without proving its implementation. These transforms require named capabilities and additional evidence.

**SEM-FIT-001:** A learned transform MUST bind an immutable fitted artifact to a versioned recipe, training input identity, split/fold identity, fit cutoff, seed where relevant, implementation version, and integrity digest. Mutable “latest model” references are not reproducible.

**SEM-FIT-002:** Each training/validation split or cross-validation fold MUST fit preprocessing on its training portion only. Evaluation and serving reuse that artifact without fitting. Vocabulary, imputation, scaling, feature selection, and target encoding are included. Supervised encoders used on training rows require an explicitly justified out-of-fold or otherwise leakage-controlled procedure.

**SEM-FIT-003:** Artifact selection MUST use the intended split, feature version, entity/time semantics, and artifact availability. A training-only artifact may be evaluated offline after T; it must not be represented as a historical production artifact unless its observed availability permits it. Artifact reuse across incompatible splits or versions MUST fail.

**SEM-CUSTOM-001:** A custom transform MUST declare its inputs/outputs, code reference and immutable digest, implementation/runtime requirements, determinism assumptions, resource limits, side effects, and acceptance evidence to the extent represented by its contract. Unrepresented semantics MUST be an explicit capability gap. Validation MUST NOT fetch or execute arbitrary custom code.

**SEM-CUSTOM-002:** Planning and execution MUST reject unsupported required capabilities. A contract-only example is allowed to pass structural validation and fail execution capability checks; this is an intentional boundary, not an implemented algorithm.

## 10. Consumers, labels, and freshness

Consumers pin a feature set/version and declare entity and timestamp inputs, historical selection mode, maximum staleness, and missing-value policy. A label definition is separate from the feature DAG.

**SEM-CONS-001:** A consumer MUST request compatible entity keys and exact feature versions. Consumer fallback cannot alter a feature's stored semantics. A default supplied for a model input must remain traceable as a consumer-side substitution.

**SEM-LABEL-001:** A label MUST declare its source, entity/time alignment, prediction anchor, horizon boundaries, availability or maturity cutoff, and treatment of censoring or incomplete follow-up. Future outcomes may define a label but MUST NOT become feature inputs or fitted preprocessing inputs through an accidental dependency.

**SEM-LABEL-002:** Examples with labels MUST test an immature horizon and late label availability. A missing future outcome is not necessarily a negative class. Train/validation/test construction MUST preserve the declared temporal and entity separation.

The baseline label horizon runs from T to T plus `horizon_seconds` with explicit `lower`/`upper` bounds. Reconstruct label source records using availability at `dataset_cutoff` before applying that horizon. `full_horizon_required: true` requires both horizon maturity and complete source coverage; `incomplete_horizon` selects exclusion or error. Only a known-complete empty horizon can use `label.empty`. The label's aggregation and source definition are independent of feature filters; a feature's predicate MUST NOT be silently applied to its label.

For nonempty eligible label rows, `count` counts rows. `any_true` requires boolean values and returns true if any value is true, otherwise null if any value is null, otherwise false. `sum` requires numeric values, and `max` requires compatible ordered values; both propagate null from an eligible value. `latest` selects the maximum event timestamp, then availability timestamp; an unresolved tie is an error and a selected null remains null. Implementations without these label capabilities MUST reject label-dataset construction explicitly; validating the consumer's label fields alone is not execution.

**SEM-FRESH-001:** Freshness checks MUST distinguish source lag, feature effective age, schedule delay, observed publication lag, and consumer maximum age. A successful job today does not establish that its source data is current. A timestamp column alone does not establish that the feature was retrievable.

**SEM-FRESH-002:** Stale or unavailable values MUST follow the consumer's declared failure/default policy with a reason. A serving implementation MUST NOT silently replace the requested historical value with the current one.

## 11. Deployments and operational contracts

Deployments separate logical semantics from adapter instances, independently replaceable execution/storage roles, generic source/output coordinates, complete field mappings, consumer bindings, refresh schedules, publication/backfill rules, capability requirements, and operating constraints. Azure Databricks is the mandatory first production implementation; no vendor implementation is required to parse the logical language.

**SEM-DEPLOY-001:** A deployment MUST bind each required logical source exactly once, declare all required target capabilities, and pin the adapter/runtime versions used in an execution manifest. Generated plans MUST preserve keys, time filters, revision reconstruction, null behavior, grain, and output contracts.

**SEM-DEPLOY-002:** Permissions, permitted purposes, classification, residency when applicable, and retention are contracts to enforce or verify at the target. Declaring them does not grant access. A retention period shorter than a requested history/replay interval MUST produce a clear limitation or error, not a partial result presented as complete.

Deployment `access` identifies read/write principals, required resource privileges, and purpose. `output_retention_seconds` states the output-retention contract. Source retention and output retention have separate roles. Residency or policy details beyond the baseline fields require an explicit adapter capability tied to an authoritative external policy or a future typed language addition. Metadata annotations alone do not enforce them; they are not inferred from an environment name.

**SEM-BUDGET-001:** Resource limits MUST bound the relevant work: scan volume, rows, time, memory, concurrency, output size, and cost where measurable. The implementation MUST stop or require an explicitly authorized larger budget when a limit would be exceeded. It MUST NOT silently sample, truncate, or substitute approximate computation.

The deployment budget records its currency, daily cost ceiling, scan-byte ceiling, output-row ceiling, memory ceiling, and concurrency ceiling. Custom/learned contracts also declare per-evaluation timeout and memory limits. SLO targets are not automatically enforced execution limits; an adapter must report how it enforces each required ceiling and which cost estimates remain unverified.

**SEM-DEPLOY-003:** Scheduling, retries, correction publication, idempotence, and backfill behavior MUST be explicit. Production execution must prove authorization and use the requested environment. This archive authorizes no deployment, release, merge, or spending.

### 11.1 Feature-store independence

**SEM-PORT-001:** The canonical semantic core MUST remain independent of feature-store SDKs, physical coordinates, and vendor-name dispatch. Adapter selection belongs to deployments. Databricks MUST be the first external production acceptance target; a local reference or mock does not satisfy that target milestone.

**SEM-PORT-002:** Deployment adapter IDs MUST be unique. Each implementation MUST use a namespaced ID and exact version. Every execution, source, target, consumer, capability, and native binding MUST resolve to an adapter with the required role. The core may represent an unknown implementation; target planning MUST reject unresolved implementations or invalid exact-version adapter configuration. A scheduled deployment MUST select an orchestrator.

**SEM-PORT-003:** Each source binding MUST pin its declared source version and map exactly every logical source column to a distinct physical field. A binding renames fields only; it MUST NOT cast, convert units, supply defaults, or change timestamp meaning. Source access uses a catalog-capable adapter and remains read-only.

**SEM-PORT-004:** Every output target MUST map exactly its feature-set membership and versions, all entity keys, each feature's value and state, and all required publication metadata to distinct physical fields. Only one target per feature-set version and storage role is allowed. Physical output resources MUST NOT repeat; format metadata is not part of resource identity. Fixture locations are read-only sources and MUST NOT be output destinations. Adapters MUST also reject physical aliases/collisions that require backend-specific resolution.

**SEM-PORT-005:** Consumer bindings MUST pin an existing consumer/version and resolve its feature set to a matching storage adapter/role target. Consumer role MUST match the deployment's publication surface. The single-surface profile uses separate deployments for independently guaranteed offline and online consumers. Consumer APIs MUST accept logical identities, keys, and declared time inputs without requiring physical table names or vendor SDK objects.

**SEM-PORT-006:** Required capabilities MUST be scoped to adapter and role. A planner MUST derive additional requirements from actual operations, transitive dependencies, native implementations, publication surfaces, and consumers; an author cannot remove a guarantee by omitting a capability string. A capability report MUST distinguish status, evidence scope, exact project/deployment/adapter identities, and execution readiness. Unsupported or unverified mandatory guarantees MUST block execution. External readiness requires live target evidence and exact implementation/runtime identities; static or mock evidence alone is insufficient.

**SEM-PORT-007:** `portable` mode MUST contain no native bindings. A native binding requires `allow_native`, exact feature and adapter identity, role, immutable code provenance, scoped capabilities, a suite containing cases for that feature/version, and migration notes. It MUST preserve the logical feature contract. Metadata extensions MUST NOT modify execution. Unsupported native behavior is a planning error, not permission to fall back to different semantics.

**SEM-PORT-008:** A deployment-only store change MUST preserve logical entity/source/relationship/feature/set/consumer identities, versions, and meaning. Physical bindings, adapter locks, deployment identity/version, and execution evidence change as appropriate. A material semantic difference MUST be surfaced for explicit version and migration review. Full project-file digests may change when bindings change and MUST NOT be confused with logical semantic fingerprints.

**SEM-PORT-009:** Publication evidence MUST identify the exposed surface and original publication origin. `publication_id`, `published_at`, and `publication_sequence` retain the original observed publication identity/order; `materialization_id` identifies the current write/import. Destination import/visibility observations MUST be recorded separately. Neither a backfill, a job-success timestamp, nor an offline commit may fabricate historical online visibility. Cross-store replay requires proven continuity and retained origin provenance for the logical service history.

**SEM-PORT-010:** Actual migration acceptance MUST include destination capabilities, retained data/history, lossless mappings, reproducible transfer/backfill, shared golden comparisons, real consumer read comparisons, and reviewed cutover/rollback conditions. A local alternate-store round trip establishes boundary separation only. A report consistency check does not authenticate evidence or certify execution readiness.

See [PORTABILITY.md](docs/PORTABILITY.md) for the role and evidence model and [MIGRATION.md](docs/MIGRATION.md) for document and store migration.

## 12. Acceptance and reproducibility

Acceptance suites carry isolated population/source fixtures with explicit as-of timestamps and either expected output rows or an expected diagnostic. Outputs must assert the full entity key, value, and any relevant state; expected diagnostics must identify the intended failure, not merely accept any exception.

`population_rows` MUST equal the canonical entity keys reconstructed from the case's supplied population source rows. Fixture source/status entries MUST include direct, transitive, and population dependencies, including explicit empty source arrays. Passing these cases establishes behavior for the supplied history and status; it does not prove production population completeness.

**SEM-TEST-001:** Acceptance MUST include decisive examples for event and availability boundaries, duplicates, corrections, retractions, null versus zero, empty population, source coverage, tenant isolation, relationship cardinality, dimension availability, derived dependencies, and publication timing for supported capabilities.

**SEM-TEST-002:** Golden expectations MUST be manually reasoned or independently derived and reviewed. Changing the implementation MUST NOT automatically rewrite them. Include metamorphic checks where helpful: a future-available row must not affect an earlier result, and adding another tenant must not affect the first tenant.

**SEM-TEST-003:** Release evidence MUST identify the exact candidate code/specification digests, dependency lockfile, environment, commands, results, skipped/unsupported checks, and independently reviewed findings. Testing one candidate and shipping a modified candidate is not sufficient evidence.

## 13. Baseline scope and extension policy

The baseline supports explicit entity populations, typed source columns, first-class relationships, revision-aware historical reconstruction, UTC elapsed-time windows, exact aggregates, recency, deterministic lookup, typed expressions, versioned dependencies, and declarative learned/custom contracts.

The reference kit may implement only a subset of that baseline. Consult the bundled verification report and its command output for what was actually executed. A complete product must implement the applicable semantic rules or emit precise unsupported-capability diagnostics.

Calendar-aware local-time windows, approximate aggregates, arbitrary SQL common semantics, unbounded stream state, arbitrary cross-entity dependencies, general model fitting, automatic production orchestration, and unproven historical-serving reconstruction are not implicitly supported. See [GAPS_AND_DECISIONS.md](docs/GAPS_AND_DECISIONS.md) for required decisions and [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) for acceptance gates.
